Why VentStream exists

A specialised solution for streaming — without the platform overhead

General platforms bring weight beyond streaming

The usual options — broker stacks, processing engines, full data platforms — cover streaming alongside schemas, connectors, state backends, analytics. Adopt any one and you take on the full surface, even when streaming is all you needed.

For a streaming-only workload that’s a lot of moving parts — and a lot of ops — you didn’t come for.

Pieces don’t add up to a pipeline

CDC tool, broker, sink, gateway — each handles its layer, none handles the seams. You own the joins, the recovery, the reconnect logic, the auth glue between them. The bridge is where outages live.

VentStream owns the full path: source to client, one binary, one ops surface.

Pipeline A · how it works

Replication that handles the join for you

You declare the join once. The engine maintains the denormalized view through every change.

  • Snapshot bootstrap. First start: reads the source tables, builds the in-memory join state, dumps to disk in one transaction.
  • Stateful multi-entity join. A change to a related row fans out to every parent document that references it — automatically, no extra consumer.
  • Crash-safe. Persistent join state on disk; the replication slot only advances past events the sink has durably written. Kill the pod and restart — no drift.
  • Composite keys, partial updates, deletes — all handled.

Pipeline B · the property that matters

Live through long idle, no drops

The most common failure mode in real-time systems: the client subscription "looks alive" but server-side state has drifted. VentStream is built so this can't happen.

  • Tested with idle gaps of 60 s, 5 min, 30 min, and 2 hours between traffic bursts.
  • Every event delivered in order. No duplicates, no reorders. 250 / 250
  • Mechanism: long-poll requests refresh the broker's consumer activity timer; server-side WebSocket pings keep TCP warm; pod-scoped reapers catch any orphans.

Operational · horizontal scale

One CDC pod, N gateway pods

CDC role

replicas: 1

Postgres replication slot is exclusive. Use a single Deployment replica, or pair with leader election.

Gateway role

replicas: N

Each pod owns its own consumers via a stable pod_id. JetStream fans out natively. Reapers are pod-scoped — safe rolling restarts.

Empirically verified: 2 gateway pods × 5,000 clients = 10,000 concurrent with 0 errors. Linear from there. multi-pod tested
