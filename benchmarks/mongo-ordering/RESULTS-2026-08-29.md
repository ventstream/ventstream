# MongoDB → OpenSearch write ordering (#117) — 2026-08-29

Question: with MongoDB as the source and the dispatcher running sink bulks in
parallel, do two writes to the same document land in the wrong order — and what
does fixing it cost?

Two binaries, same workload, same machine:

- **prefix** — `main` at `a7c0244`: MongoDB events carry no source version.
- **fixed** — this branch: every change event carries the change's
  `clusterTime` (packed `time << 31 | increment`) as
  `ventstream.cdc.source_version`; snapshot rows carry the scan-start
  `operationTime` as a floor. OpenSearch applies it as the external document
  version (`external_gte`) and refuses any write older than the one it holds.

Harness: `benchmarks/mongo-ordering/run.sh` (release builds, mongo:7.0
single-member replica set, opensearchproject/opensearch:2.17.1 single node,
Docker Desktop on an Apple-silicon laptop). Each run seeds the collection,
bootstraps a fresh engine and index, then applies `ROUNDS` full passes of
`replaceOne` over `DOCS` hot documents so every document's consecutive writes
are `DOCS` events apart in the oplog — a few bulks at `BATCH` events each,
inside the parallel in-flight window.

Columns: **ooo-bulks** — bulks the jitter proxy forwarded ahead of an earlier
bulk carrying strictly older rounds (writes that reached OpenSearch out of
source order; identical exposure for both binaries). **regressions** — times a
50 ms sampler saw a document's `round` go *backwards* (an older write applied
after a newer one; a lower bound, since a regression overwritten between two
samples is invisible). **stale** — documents whose final state is not the last
write. **409s** — stale writes the fixed binary's sink refused. **doc0
_version** — OpenSearch's stored version for one document: the internal
counter (1 + writes applied) for an unversioned binary, the packed
`clusterTime` for a versioned one.

## Hot documents through 0–100 ms sink jitter

20 documents × 300 rounds = 6,000 change events, `BATCH=20` (one round per
bulk), sink writes routed through `jitter-proxy.py`, which holds each bulk for
a random 0–100 ms before forwarding — the network jitter, uneven bulk sizes and
multi-node clusters a real deployment has and a local single node does not.

| binary | parallel | secs | events/s | bulks | ooo-bulks | regressions | stale | 409s | doc0 _version |
|---|---|---|---|---|---|---|---|---|---|
| prefix | 4 | 5.16 | 1,163 | 300 | 244 | **1,340** | **20 / 20** | 0 | 301 |
| prefix | 1 *(the stopgap)* | 19.04 | 315 | 300 | 0 | 0 | 0 | 0 | 301 |
| fixed | 4 | 5.00 | 1,200 | 300 | 282 | **0** | **0** | 2,880 | 7679514654686578321 |
| fixed | 1 | 18.80 | 319 | 300 | 0 | 0 | 0 | 0 | 7679514706226186276 |

- **The defect is real and total.** Pre-fix at `parallel=4`, 244 of 300 bulks
  overtook an older one; the sampler caught 1,340 backwards moves; and **every
  one of the 20 documents ended in the wrong state** — its `_version` of 301
  says all 300 writes were applied, in whatever order they arrived.
- **The stopgap works and costs 3.7×.** Serialising bulks (`parallel=1`) is
  correct on either binary, at 315 events/s instead of 1,163 — each bulk pays
  the full round trip alone.
- **The fix is correct at full parallelism, for free.** Same exposure (282
  overtaking bulks), zero regressions, zero stale documents, 2,880 stale writes
  refused by the sink's version check (a refused write is a no-op, not a
  retry — the H18 rule), and throughput equal to the pre-fix parallel run.

## Same workload without jitter

200 documents × 200 rounds = 40,000 events, `BATCH=100`, direct to OpenSearch.

| binary | parallel | secs | events/s | regressions | stale | 409s | doc0 _version |
|---|---|---|---|---|---|---|---|
| prefix | 4 | 1.97 | 20,315 | 0 | 0 | 0 | 201 |
| prefix | 1 | 1.83 | 21,882 | 0 | 0 | 0 | 201 |
| fixed | 4 | 1.87 | 21,412 | 0 | 0 | **473** | 7679515028348761193 |
| fixed | 1 | 1.76 | 22,772 | 0 | 0 | 0 | 7679515071298405497 |

- Throughput is the same across all four (20–23k events/s; the spread is
  run-to-run noise on a laptop). Stamping one header per event and having
  OpenSearch compare a version costs nothing measurable.
- Even on a local single node with no jitter, **473 writes arrived out of
  order** at `parallel=4` — 1.2 % of the workload — and the fixed binary
  refused them. The pre-fix binary applied them; the sampler is too coarse to
  see a one-round regression at 20k events/s, but the 409 count on the fixed
  run is a direct measurement of the same exposure.

## Two things the harness had to learn

- **`updateLookup` hides the defect for updates.** A change event's
  `fullDocument` under `updateLookup` is the document as it is when the event
  is *read*, not when it was written. With a backlog, every queued event
  already carries the newest state, so an out-of-order apply overwrites the
  document with the same newest state and the *final* state comes out right by
  accident — while the pipeline also looks finished with thousands of events
  still queued. `replaceOne` (and inserts, and deletes) carry the image of
  their own operation, and there the reordering shows plainly. The first draft
  of this harness used `$set` and reported zero stale documents for the pre-fix
  binary; that number was an artefact, not a result.
- **A final-state check is the wrong metric.** A later round almost always
  lands eventually, so only the very last pair of bulks decides whether a
  document ends stale. The sampler's regression count and the fixed binary's
  409 count measure the reordering itself.

Reproduce:

```sh
cargo build --release -p ventstream --bin ventstream
JITTER_MS=100 DOCS=20 ROUNDS=300 BATCH=20 \
  benchmarks/mongo-ordering/run.sh prefix=<main binary> fixed=target/release/ventstream
DOCS=200 ROUNDS=200 BATCH=100 \
  benchmarks/mongo-ordering/run.sh prefix=<main binary> fixed=target/release/ventstream
```
