# Container benchmark results - 2026-07-20

## Test system

- Host: Apple Silicon macOS, 14 logical CPUs, 36 GiB RAM
- Docker Desktop: 7 CPUs, 8 GiB RAM
- Engine limit per case: 2 vCPUs, 1 GiB RAM
- Engine image: `sha256:61cd785babfd8f209fef...`
- Source revision: `0f28c01b07caeb963e1763a65f75487696d92c26` plus the local performance changes
- OpenSearch: 2.17.1, 2 vCPUs, 2.25 GiB, 1 GiB JVM heap
- Payload: 256 bytes
- OpenSearch during load: refresh disabled, zero replicas

Docker CPU is expressed as a percentage of one core, so 200% is the nominal
ceiling of the two-vCPU engine container. Cgroup memory is Docker's charged
working set; RSS HWM is the engine process high-water mark from `/proc`.

MySQL's maximum profile was only 0.4% faster than throughput and used more
CPU, so throughput is the operational recommendation. MongoDB was fastest and
materially smaller with balanced tuning. PostgreSQL and Kafka both regressed
when moved from throughput to maximum.

Neo4j remained source-bound at about 5% mean engine CPU. More engine replicas
or larger internal queues will not address that result; query/fan-out work and
the Neo4j service are the next optimization boundary.

## Realtime tuning findings

- NATS Core uses central fan-out, so it keeps a 65,536-event per-connection
  mailbox for this burst profile. At 200 clients it used 516 MiB process RSS;
  connection admission and pod scaling remain necessary production controls.
- Durable raw NATS and Redis sessions use a 1,024-event mailbox. Their
  connection-specific pumps now wait up to one second for a healthy client to
  drain before returning an explicit slow-consumer error.
- GraphQL NATS and Redis use a 1,024-event connection broadcast. The pump
  applies the same bounded wait and retains the existing `SUBSCRIPTION_LAGGED`
  terminal signal if an operation cannot drain.
- GraphQL Redis uses a 100-record broker read batch; raw Redis uses 1,000.
- Before bounded backpressure, raw Redis exceeded 1 GiB and GraphQL Redis
  exceeded 2 GiB during the four-million-delivery test. Payload copies were
  accumulating in every connection queue because Redis acceptance is a no-op.
- After the fix, the same cases passed at 131 MiB and 378 MiB RSS respectively,
  and throughput improved. This was an implementation defect, not a Redis
  capacity requirement.

## Defects found

PostgreSQL SQL mode inferred primary-key types by querying a sample row. An
empty table therefore defaulted a numeric primary key to text and later issued
an invalid `bigint = ANY(text[])` query. Type discovery now queries PostgreSQL
catalog metadata independently of table contents, with an integration test for
startup before the first insert.

The sustained realtime pass found provider-dependent missing backpressure.
Redis live sessions can advance immediately after enqueue because they have no
broker acknowledgement. Large per-connection buffers therefore retained a
copy of each pending delivery and exhausted one- and two-GiB containers. Raw
and GraphQL durable pumps now apply time-bounded backpressure before enqueue;
genuinely slow consumers still receive a terminal resumable failure.

## Interpretation

These numbers are the ceiling of this local, resource-limited stack, not a
universal hardware claim. PostgreSQL, MongoDB, and Neo4j did not saturate the
two engine CPUs, indicating source or sink limits. Kafka and high-fan-out
realtime cases came closest to saturating the engine. Production sizing should
rerun this harness against the intended managed databases, network, payload
shape, index mappings, and join complexity.
