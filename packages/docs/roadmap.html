Production readiness ~1 week

The work that takes v0.1 from "demo-quality" to "I can put this in front of a paying customer."

  • JWT auth on connection_init payloads and HTTP headers. Today: trust any non-empty token. Single seam (auth::extract) to swap.
  • Persistent join state via redb for Pipeline A. Engine restart shouldn't require full WAL replay from the slot's earliest LSN.
  • Leader election (k8s Lease or Postgres advisory lock) so the CDC role can run as active + warm standbys.
  • Observability: wire ventstream-telemetry into Prometheus metrics + OpenTelemetry tracing. Connection count, consumer count, throughput, JetStream lag.
  • Docker image + Helm chart so customers can helm install ventstream.

Cosmo replacement story ~3-5 days · commercial

Focused commercial work to convert the v0.1 engine into something we can pitch to federated-GraphQL deployments.

  • "Drop-in replacement" guide: step-by-step swap of Cosmo's built-in WebSocket layer with VentStream while keeping Cosmo as the federation router.
  • Side-by-side benchmark: same federated supergraph, Cosmo's WS vs VentStream's. Consumer count over a 1-hour churn workload. Real numbers.
  • Cosmo NATS-subject compatibility notes: Cosmo expects specific subject shapes for its @edfs__natsSubscribe directive. Document the translation so existing Cosmo subgraph code works against VentStream as the backbone.
  • Landing page: positioning, the consumer-leak story, real benchmark numbers.

Pipeline A depth ~1-2 weeks

Only worth doing if customers are asking for CDC specifically rather than the WS / federated-subs story.

  • Nested joins (multi-level chains: order → buyer → contact_person) — currently one level only.
  • Junction-table M-to-M (e.g. orders ↔ tags via a junction table).
  • Eager bootstrap via slot snapshot: adding a new join to an existing dataset can replay history instead of starting from "now".
  • TRUNCATE handling in join state (currently logs and skips).
  • AWS SigV4 auth for OpenSearch Service (AWS-hosted).
  • More sinks: Algolia, Typesense, Elasticsearch, custom HTTP.

Pipeline B polish smaller items

  • Pong-timeout integration test wired into CI (currently runs locally via raw TCP/WS framing).
  • Multipart subscription transport (Apollo's multipart/mixed alternative to WS) — useful where WS is blocked.
  • Persistence on the WS side: per-pod connection registry survives soft restart.
  • Tenant-scoped subject permissions in the manifest (currently a tenant can subscribe to any pattern under their prefix).

Future / not in scope for v1

  • gRPC SDK ingest — explicitly rejected during design. Developers publish direct to NATS via the SDK. Adding an engine ingest gateway between them adds a debugging layer with no commensurate value.
  • Schema registry for data — opaque payloads in v1. May add JSON Schema registration in v2 if customers ask.
  • VentStream as a federation router — we're a subgraph, not a router. Apollo Router and Cosmo Router are the routers; we cooperate via standards.
  • Multi-tenancy at the NATS-account level — currently tenant scoping is via subject prefix + auth-time check. NATS accounts give physical isolation; v2.

Architectural invariants — do not violate

These are the non-negotiable contracts established in v0.1. Any change to the code paths involved must preserve these:

  1. One JetStream consumer per WebSocket connection. Not per subscription. Not per service. Per connection. This is what enables resume-on-reconnect and per-client flow control.
  2. Three-layer cleanup hierarchy. RAII drop guard + inactive_threshold + reaper. Removing any one of them brings the Cosmo leak back.
  3. Strict subject grammar. 7 segments, character classes enforced, validated by both SDK and gateway.
  4. Deterministic doc IDs on Pipeline A. Re-emits overwrite, never duplicate.
  5. Workspace lints — unwrap_used, expect_used, panic, indexing_slicing denied outside tests. Don't relax.

Open questions worth thinking about

  • Should the WS gateway support multipart/mixed subscriptions for clients behind WS-blocking proxies?
  • Does Pipeline B want at-least-once semantics by default, or stay at the JetStream "ack to advance cursor" model?
  • Is there a clean way to expose Pipeline A's join state for "snapshot this entity as it looks right now" reads — turning the engine into a queryable cache?
  • When do we add multiple sinks per pipeline? (Today: source → joins → ONE sink. Multi-sink is a Phase 1+ config schema decision.)
