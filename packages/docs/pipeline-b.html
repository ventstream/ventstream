Pipeline B · WebSocket fan-out

Application events published via NATS, fanned out to subscribed WebSocket clients with per-connection durable cursors. Three-layer cleanup means no Cosmo-style leaks.

The wire envelope

Every event flowing through the bus carries this envelope. The SDK fills in id, event, received_at, and schema_version; developers supply the business identity and payload.

{
  "id": "01KSA...",                            // ULID, set by SDK, idempotency key
  "event": "orders.order.status_changed",      // {domain}.{entity.kind}.{action}
  "tenant": "acme",                            // verified against publisher's auth
  "entity_id": "order_123",                    // final routing-subject segment
  "actor":  { "kind": "user",  "id": "user_456" },  // optional audit principal
  "occurred_at": "2026-05-23T03:55:00Z",       // when the business event happened
  "received_at": "2026-05-23T03:55:01Z",       // when SDK shipped to bus
  "schema_version": 2,
  "data": { "from": "pending", "to": "confirmed" },  // dev-defined, opaque
  "metadata": {
    "trace_id":       "01KSA...",              // optional W3C trace context
    "correlation_id": "01KSA...",              // optional app-level correlation
    "causation_id":   "01KSA..."               // optional parent event id
  }
}

Field rules

  • actor is optional — include it when an auditable user or service caused the event.
  • data is opaque — the engine doesn't introspect it. v1 by design.
  • occurred_at ≠ received_at is normal — backfills, delayed publishes, async workflows. Both are needed.
  • schema_version bumps only on envelope shape changes (not data shape).
  • Unknown envelope fields → rejected (deny_unknown_fields in serde).

The subject grammar

Every event's NATS routing key follows a strict ID-last pattern. The event name may contain one or more dot-separated segments. The SDK builds it; the gateway validates it.

vs.t.{tenant}.{event}.{entity_id}
SegmentRuleExample
vsLiteral namespacevs
t.{tenant}Tenant scope. Enforced by NATS JWTt.acme
{event}One or more [A-Za-z0-9_-]+ segmentsorders.order.status_changed
{entity_id}Final segment; [A-Za-z0-9_-]+, max 128order_123

Subscribe patterns

NATS wildcards (* for one segment, > for trailing) are supported. Clients pass the unanchored form; the gateway prepends vs.t.{tenant}. from auth.

orders.>                                # everything orders-related
orders.order.status_changed.*            # status changes for any order
orders.order.status_changed.order_123    # one event class for one order
*.order.deleted.*                        # any order deletion in this tenant

Publishing — @ventstream/sdk

import { VentStream } from "@ventstream/sdk";

const vs = new VentStream({
  servers: "nats://localhost:4222",
  name: "orders-api",          // shown in NATS server logs
});
await vs.connect();

await vs.publish({
  tenant: "acme",
  domain: "orders",
  action: "status_changed",
  entity: { kind: "order", id: "order_123" },
  actor:  { kind: "user",  id: "user_alice" },
  data: { from: "pending", to: "confirmed" },
  // optional:
  occurredAt: new Date(),
  metadata: { trace_id: "abc...", correlation_id: "req_xyz" },
});

await vs.close();

Backpressure policies

Per-publish or per-connection default:

PolicyBehaviorUse
"buffer" (default)Let nats.js buffer in memoryCommon case; fastest
"block"await publish() only resolves after flushSafest; lowest throughput
"drop"If connection is closed, drop silentlyFire-and-forget telemetry

What gets rejected at publish time

The SDK validates before any bytes hit the network:

✗ tenant: only [a-z0-9_-] allowed              ← caller passed "ACME"
✗ action: only [a-z0-9_-] allowed              ← caller passed "Status Changed"
✗ entity.id: only [A-Za-z0-9_-] allowed        ← caller passed "ord.with.dots"

Subscribing — @ventstream/client

import { VentStreamClient } from "@ventstream/client";

const client = new VentStreamClient({
  url: "ws://localhost:4040/ws",
  tenant: "acme",
  token: "demo",              // JWT in v1.5; trusted-string in v1
  reconnect: true,            // auto-reconnect on disconnect (default)
  reconnectDelayMs: 500,      // base delay; backs off up to 30s with jitter
});

await client.connect();

const sub = client.subscribe(
  "orders.order.status_changed.*",
  (event, ctx) => {
    console.log(ctx.subject, event.entity_id, event.data);
  },
);

// later:
sub.unsubscribe();
await client.close();

Reconnect + subscription replay

If the WebSocket drops, the client reconnects with jittered exponential backoff (capped at 30s) and replays every active subscription against the new connection. The application code doesn't need to handle this — same callbacks fire, same way.

The three-layer cleanup hierarchy

The bespoke design choice (one durable JetStream consumer per WS connection) means cleanup must be bulletproof. Three independent mechanisms:

┌──────────────────────────────────────┐ Layer 1: │ RAII drop guard in connection task │ (~ms) │ fires on EVERY exit path: │ │ graceful close, panic, ping │ │ timeout, slow-consumer eviction │ │ → js.delete_consumer(name) │ └──────────────────────────────────────┘ ▼ ┌──────────────────────────────────────┐ Layer 2: │ inactive_threshold on the consumer │ (~5 min) │ JetStream server-side auto-delete │ │ if no activity for N seconds. │ │ Catches: │ │ - kill -9 (drop guard never ran) │ │ - OOM kill │ │ - pod evicted by k8s │ └──────────────────────────────────────┘ ▼ ┌──────────────────────────────────────┐ Layer 3: │ Reaper task: every ~60s, list │ (~min) │ consumers under vs.t.>.p.{me}.c.> │ │ and diff against THIS pod's │ │ connection registry. Delete the │ │ orphans. │ └──────────────────────────────────────┘

Each layer's tests live in packages/example/cleanup-layers-test.mjs — all three are run against a live NATS cluster with deterministic outcomes.

Consumer naming

Every consumer is named vs-t-{tenant}-p-{pod_id}-c-{connection_id}. The reaper substring-matches on -p-{pod_id}-c- to identify "consumers this pod owns" — no cross-pod coordination required for cleanup. Each pod cleans up after itself.

Slow consumer disconnect

A slow WS client cannot stall a fast publisher. The mailbox between the consumer pump and the WS writer task is bounded (default 256 events). When it overflows:

  1. The pump detects the try_send failure and calls registry.remove(connection_id).
  2. That drops the registry's Sender clone; the connection task's Receiver returns None.
  3. The connection task closes the WebSocket and exits.
  4. The RAII drop guard fires, deleting the JetStream consumer.
  5. The client sees the WS close and reconnects (auto-reconnect default).

Server-side this happens in ~20ms; client-side the close arrives once the OS+WS buffers drain (typically ~1s depending on how full they were).
