Pipeline A · CDC + joins

Stream Postgres changes through stateful joins to a denormalized index. Foreign-side mutations re-emit the primary doc; sync-on-miss covers ordering gaps. One document per logical row in the sink, even across replays.

What this pipeline does

Standard CDC tools push raw row changes — you receive an event saying "the orders table had row X updated." If you want a denormalized view (an Order document containing the line items, the buyer's name, the shipping address), you either pre-build it on every update or you assemble it in a downstream pipeline.

VentStream lets you declare the join graph in YAML. The join engine maintains the necessary indexes in memory, applies sync-on-miss when a row is referenced before its primary arrives, and re-emits the primary document whenever any of its dependencies change. Output: one composed document per logical row, idempotent via deterministic _id.

Postgres setup

The source uses pgwire-replication (pgoutput plugin), so the database needs logical replication enabled.

1. Enable logical replication

# postgresql.conf
wal_level = logical
max_wal_senders = 10
max_replication_slots = 10

Restart Postgres after the change.

2. REPLICA IDENTITY FULL on every table you join across

This makes UPDATE and DELETE WAL records carry the full old row, not just the primary key. Without it, foreign-side updates may miss state needed for join maintenance.

ALTER TABLE orders         REPLICA IDENTITY FULL;
ALTER TABLE shipments        REPLICA IDENTITY FULL;
ALTER TABLE order_addresses    REPLICA IDENTITY FULL;
ALTER TABLE order_buyers    REPLICA IDENTITY FULL;
ALTER TABLE line_items         REPLICA IDENTITY FULL;

3. Publication + replication slot

CREATE PUBLICATION vspub FOR TABLE orders, shipments, order_addresses, order_buyers, line_items;
SELECT pg_create_logical_replication_slot('vsslot', 'pgoutput');

Join configuration

The YAML declares one or more join definitions. Each has a primary table (the one whose changes produce the composed document) and any number of related tables that get embedded into the document.

# joins.yaml — the orders example we tested with
joins:
  - name: orders_denormalized
    primary:
      table: public.orders
      pk: order_id          # single-column PK

    related:
      # 1-to-1 simple FK
      - id: shipment
        table: public.shipments
        pk: shipment_id
        join_on: { from: shipment_id, to: shipment_id }
        cardinality: one

      # 1-to-1 simple FK
      - id: address
        table: public.order_addresses
        pk: address_id
        join_on: { from: address_id, to: address_id }
        cardinality: one

      # 1-to-1 with COMPOSITE PK (order_id, buyer_id) but joined on order_id only.
      # The engine resolves this via its `foreign_by_fk` secondary index.
      - id: buyer
        table: public.order_buyers
        pk: [order_id, buyer_id]
        join_on: { from: order_id, to: order_id }
        cardinality: one

      # 1-to-many
      - id: line_items
        table: public.line_items
        join_on: { from: order_id, to: order_id }
        cardinality: many
        sort_by: date          # optional ordering of the embedded array

Key fields

  • primary.pk — single-column or composite. Composite is [col_a, col_b].
  • related[].pk — same. Used to identify each row in the related table for state storage.
  • related[].join_on.from / to — columns on the primary and related sides. Don't have to be primary keys (see buyer above — joined on order_id, not the full composite PK).
  • cardinality — one embeds a single object; many embeds an array.
  • sort_by — orders the embedded array. Optional.
  • select — columns to project into the embedded object; omit to embed the whole row. If you set select on a many child whose deletes must propagate under REPLICA IDENTITY DEFAULT, you must include the child's PK in the list. A child DELETE under DEFAULT only carries the child PK in the WAL (not the parent FK), so the engine recovers the parent by looking up the embedded child PK in the sink — if the PK isn't embedded, the lookup matches nothing and the child delete won't propagate. An empty select embeds everything, so the PK is always present.

What the engine does on each event

For a primary INSERT or UPDATE:

  1. Update reverse indexes so the engine remembers which primaries reference which foreign rows.
  2. For each related definition, look up the related row(s) in state. If missing, fetch via SELECT on a separate connection (sync-on-miss).
  3. Compose the document by embedding the related rows into the primary's JSON.
  4. Emit the composed document with a deterministic ventstream.doc.id header.

For a related INSERT, UPDATE, or DELETE:

  1. Look up the reverse index: which primaries reference this foreign row?
  2. For each affected primary, re-compose with the new related state and re-emit.

This is the "foreign-side re-emit" mechanism — the same primary document gets re-published every time anything it depends on changes, so the sink stays consistent without any extra logic.

Deterministic _id for the sink

Re-emitting the same primary document many times would normally create lifecycle copies in OpenSearch. We avoid that by setting a ventstream.doc.id header on every emit:

ventstream.doc.id = {primary_table}:{primary_pk}

# Examples:
#   public.orders:["order-002"]
#   public.users:["user_alice"]
#   public.invoices:["INV-2026","line-3"]   # composite PK

The OpenSearch sink uses this header as _id, overwriting the same document instead of indexing a new one.

What's tested

The orders schema (orders × shipments × order_addresses × order_buyers[composite-PK] × line_items) seeded into a local Postgres on port 5433. Every foreign-side mutation was exercised:

  • UPDATE on a parent — all dependent primaries re-emitted with the new field
  • UPDATE on a address (1-to-1 child) — only the affected primaries re-emitted
  • UPDATE on a buyer (composite-PK 1-to-1 child) — only the affected primaries re-emitted
  • UPDATE on a line item (1-to-many child) — the nested array reflects the change
  • INSERT of a new line item — the array grows
  • DELETE of a line item — the array shrinks
  • Idempotency check — 3 orders produce 3 OpenSearch documents regardless of how many re-emits happened

Snapshot bootstrap (full sync for existing data) v0.1

By default the CDC pipeline only sees changes that happened after the slot was created. To populate the sink with existing rows on first deployment, opt in:

VS_ROLES=cdc \
VS_PG_BOOTSTRAP_MODE=snapshot \
VS_PG_BOOTSTRAP_CHUNK_SIZE=10000 \
VS_JOINS_YAML=joins.yaml \
VS_PG_* VS_OS_* ... \
  ./ventstream

When the engine starts:

  1. Connects to Postgres on a standalone connection (separate from the replication slot).
  2. Checks pg_replication_slots. If the slot already exists, skips the bootstrap and starts streaming normally.
  3. If the slot doesn't exist, creates it (pgoutput plugin) — concurrent writes get captured in the WAL.
  4. For each table participating in the joins (related tables first, then primaries), SELECTs all rows in chunked pages ordered by primary key.
  5. Emits each row as a synthetic INSERT event into the source bus. The join engine treats them identically to WAL-derived inserts.
  6. Hands off to pgwire-replication for normal streaming.

Tables and primary keys are derived from your joins YAML — no second list to maintain. Composite PKs use Postgres row-tuple comparison ((a,b) > ($1,$2)) for pagination.

v1 caveats

Non-transactional. v1 reads with a regular REPEATABLE READ transaction, not the slot's exported snapshot. A row updated during the snapshot window can race — the deterministic doc-ID in the sink makes this mostly harmless for search-index workloads, but for audit/compliance use cases that require transactional consistency, v2 will use CREATE_REPLICATION_SLOT ... USE_SNAPSHOT.
No resumability. Engine death mid-snapshot restarts from scratch. Pairs naturally with the redb persistent-state work on the roadmap.
No per-join trigger. Adding a new join to an existing pipeline still relies on sync-on-miss for backfill. Per-join scan (Mode 2) is a follow-up.

Manual resync at any time v0.1

Once the engine is running you can trigger a full re-sync on demand. Opt in with VS_ADMIN_LISTEN and the binary exposes a small admin HTTP server alongside the CDC engine. Useful for drift repair, adding new joins, or periodic reconciliation.

VS_ADMIN_LISTEN=127.0.0.1:4042 \
... other config ... \
  ./ventstream

# Then, while it's running:
curl -X POST http://127.0.0.1:4042/admin/resync                          # all tables
curl -X POST http://127.0.0.1:4042/admin/resync?tables=public.orders      # scoped
curl http://127.0.0.1:4042/admin/healthz                                 # liveness

Response:

{
  "tables_processed": ["public.shipments", "public.orders"],
  "stats": { "total": 4, "elapsed_ms": 1 }
}

Concurrency: single-flight. A second resync while one is running returns 409 Conflict immediately; the first continues uninterrupted.

Safety: the resync runs alongside normal WAL streaming. A row that arrives via both paths (snapshot and WAL) overwrites the same destination doc thanks to the deterministic _id — no duplicates, no consistency drift.

Auth: none in v1. Bind to 127.0.0.1 only and rely on network isolation, or front it with a reverse proxy that adds auth.

Persistent join state v0.1

By default the join engine keeps state in memory. Restart = cold start. For large pipelines, set VS_JOINS_STATE_DIR=/path/to/dir and every mutation gets mirrored to a redb database under that directory. On startup, the saved state is loaded into the in-memory maps before WAL streaming resumes.

VS_ROLES=cdc \
VS_JOINS_STATE_DIR=/var/ventstream/state \
VS_JOINS_YAML=joins.yaml \
VS_PG_* VS_OS_* ... \
  ./ventstream

Why this matters: foreign-side re-emit relies on the primary_reverse index that says "this primary row references this FK value." Without persistence, that index is empty after restart, so a foreign UPDATE after restart wouldn't re-emit the primary docs that depend on it. With redb the index survives, and re-emit Just Works the same way it did before restart.

v1 caveats

Not event-atomic. A CDC event triggers multiple state mutations; v1 commits each as its own redb transaction. A crash mid-event leaves the on-disk state with the partial set applied. Sync-on-miss + foreign-side re-emit eventually correct most cases. Full event atomicity comes with sink-ACK-gated LSN advance.
Write-through, per-mutation fsync. One redb commit per state mutation. Fine for most workloads; for very high event rates (10k+/sec sustained), batched commits are a v2 add. Documented in persistence.rs.
Nested joins. One level of join is supported. order → buyer → contact_person requires manual JSON post-processing for now.
TRUNCATE. If you TRUNCATE a participating table, the engine logs a warning and skips it. State doesn't auto-clear. Restart the engine for a clean slate.
