VentStream

Real-time event infrastructure as a single-binary engine. CDC with stateful joins on one side, durable WebSocket fan-out with proper consumer cleanup on the other. Built in Rust.

What it does

Two independent event pipelines, both running in the same binary, role-selectable per pod:

┌─────────────────────────────────────────────────────────────────────────┐ │ Pipeline A — CDC + denormalized indexing │ │ │ │ Postgres WAL ──► Join engine ──► OpenSearch (or Algolia / Typesense) │ │ (slot) ▲ │ │ │ │ │ joins.yaml: 1-1, 1-N, composite PKs, partial-FK, │ │ foreign-side re-emit, sync-on-miss backfill │ └─────────────────────────────────────────────────────────────────────────┘ ┌─────────────────────────────────────────────────────────────────────────┐ │ Pipeline B — Durable WebSocket fan-out │ │ │ │ SDK ──► NATS JetStream ──► WS gateway ──► clients │ │ (publish) (one durable │ │ consumer per │ │ connection + │ │ 3-layer cleanup) │ │ │ │ Or: Apollo Client speaks graphql-transport-ws to the same engine — │ │ generic events(subject) field or typed subscriptions from a │ │ manifest. Works as a federated subgraph behind any router. │ └─────────────────────────────────────────────────────────────────────────┘

Why it exists

Two real-world problems that show up at scale in federated GraphQL / data-platform environments:

  1. Postgres → search index with joins is a pipeline, not a primitive. Most CDC tools push raw table rows. Reconstructing the denormalized doc (an Order with its line items, its buyer, its shipping address) becomes Logstash / Kafka Streams / a custom service. VentStream lets you declare the joins in YAML and emits the composed document.
  2. WebSocket subscription gateways leak resources. Federation routers (notably Cosmo) have a documented bug where JetStream durable consumers pile up — 733 zombies in production for one team. VentStream's WS path uses a three-layer cleanup hierarchy that makes leaks structurally hard.

Both problems have the same shape underneath — event routing with state — which is why the same engine handles both.

What's shipped v0.1

Pipeline A (CDC)

  • Postgres logical replication via pgwire-replication (pgoutput plugin)
  • Stateful join engine: 1-to-1, 1-to-many, composite primary keys, partial-FK joins, foreign-side re-emit, sync-on-miss backfill
  • OpenSearch bulk sink with idempotent index actions, NDJSON framing, per-item DLQ, partial-failure retry
  • Deterministic per-logical-row document IDs (re-emits overwrite the same doc instead of leaving lifecycle copies)
  • Validated against a realistic orders schema (orders + shipments + addresses + buyers + line items) with composite-PK + foreign-side mutations

Pipeline B (WS)

  • Native WebSocket gateway speaking VentStream's own protocol (axum + NATS)
  • Per-connection durable JetStream consumers — clients resume their own cursor on reconnect
  • Three-layer cleanup hierarchy: RAII drop guard, inactive_threshold on the consumer, periodic reaper
  • Slow consumer disconnect (no slow client takes down a fast publisher)
  • TypeScript SDKs: @ventstream/sdk (publisher) and @ventstream/client (subscriber, browser + Node)

GraphQL gateway includes Federation

  • graphql-transport-ws endpoint — Apollo Client connects natively, no custom Link
  • Model 1: generic events(subject) subscription with opaque JSON payload
  • Model 2: typed subscription fields declared in a YAML manifest with args + response shape
  • Federation Flavor B verified end-to-end through Cosmo Router with entity-ref stitching

Single binary, role-based deployment

The same binary runs as any subset of the three roles. Each role is independent — they share the engine kernel (config, logging, shutdown) but their data paths don't intersect.

# CDC role only (production: 1 active + N warm standbys)
VS_ROLES=cdc ./ventstream

# WS gateway only (horizontally scaled via HPA)
VS_ROLES=ws ./ventstream

# GraphQL gateway only (drop-in Apollo Client backend)
VS_ROLES=graphql ./ventstream

# Everything together (single-node demos, small-tenant deployments)
VS_ROLES=cdc,ws,graphql ./ventstream
