Getting started

Clone, build, run NATS, fire your first event from a TypeScript publisher and receive it in an Apollo Client subscriber — in under ten minutes.

Prerequisites

For Pipeline B (the simplest setup), you only need Rust + nats-server. The walkthrough below uses that path.

1. Clone and build

git clone https://github.com/ventstream/ventstream
cd ventstream
cargo build --release -p ventstream

First build pulls a few hundred dependencies — give it a few minutes. Subsequent builds are incremental.

2. Start NATS with JetStream

# macOS
brew install nats-server

# Run in a separate terminal
mkdir -p /tmp/ventstream-jetstream
nats-server -js -sd /tmp/ventstream-jetstream

-js enables JetStream. -sd picks a data directory — JetStream writes durable messages there.

3. Run the engine in WS mode

The minimum config to start the WS gateway with JetStream:

VS_ROLES=ws \
VS_WS_LISTEN=127.0.0.1:4040 \
VS_WS_NATS_URL=nats://127.0.0.1:4222 \
VS_WS_JETSTREAM=1 \
VS_WS_JS_STREAM=ventstream \
VS_WS_JS_POD_ID=podA \
RUST_LOG=info \
  ./target/release/ventstream

You should see logs ending with:

INFO ventstream_ws::jetstream: JetStream stream created stream=ventstream
INFO ventstream_ws::server:    JetStream mode active stream=ventstream pod_id=podA
INFO ventstream_ws::server:    ws gateway listening listen=127.0.0.1:4040 jetstream=true

4. Run the GraphQL gateway alongside (optional)

If you want Apollo Client to be able to connect via standard graphql-transport-ws, also enable the graphql role:

VS_ROLES=ws,graphql \
VS_WS_LISTEN=127.0.0.1:4040 VS_WS_NATS_URL=nats://127.0.0.1:4222 \
VS_WS_JETSTREAM=1 VS_WS_JS_STREAM=ventstream VS_WS_JS_POD_ID=podA \
VS_GRAPHQL_LISTEN=127.0.0.1:4041 VS_GRAPHQL_NATS_URL=nats://127.0.0.1:4222 \
VS_GRAPHQL_STREAM=ventstream VS_GRAPHQL_POD_ID=podA \
RUST_LOG=info \
  ./target/release/ventstream

The GraphQL HTTP endpoint is at http://127.0.0.1:4041/graphql, the WS endpoint at ws://127.0.0.1:4041/graphql/ws.

5. Publish your first event

From a Node project (or run inside packages/example):

import { VentStream } from "@ventstream/sdk";

const vs = new VentStream({
  servers: "nats://127.0.0.1:4222",
  name: "demo",
});
await vs.connect();

await vs.publish({
  tenant: "acme",
  domain: "orders",
  action: "status_changed",
  entity: { kind: "order", id: "order_001" },
  actor:  { kind: "user",  id: "user_alice" },
  data: { from: "pending", to: "confirmed" },
});

await vs.close();

The SDK builds the protocol-v2 envelope (ULID id, timestamps, schema version), validates the subject grammar, and publishes to NATS subject vs.t.acme.orders.order.status_changed.order_001.

6. Subscribe from a client

Option A — Native VentStream client

import { VentStreamClient } from "@ventstream/client";

const client = new VentStreamClient({
  url: "ws://127.0.0.1:4040/ws",
  tenant: "acme",
  token: "demo",
});
await client.connect();

client.subscribe("orders.order.status_changed.*", (event) => {
  console.log(event.entity_id, event.data.from, "->", event.data.to);
});

The subscription pattern is unanchored — the gateway prepends the tenant from the connection token.

Option B — Apollo Client via the GraphQL gateway

import { ApolloClient, InMemoryCache, gql, split, HttpLink } from "@apollo/client";
import { GraphQLWsLink } from "@apollo/client/link/subscriptions";
import { createClient } from "graphql-ws";
import { getMainDefinition } from "@apollo/client/utilities";

const httpLink = new HttpLink({
  uri: "http://127.0.0.1:4041/graphql",
  headers: { Authorization: "Bearer demo", "X-VS-Tenant": "acme" },
});

const wsLink = new GraphQLWsLink(
  createClient({
    url: "ws://127.0.0.1:4041/graphql/ws",
    connectionParams: () => ({ authToken: "demo", tenant: "acme" }),
  }),
);

const link = split(
  ({ query }) => {
    const def = getMainDefinition(query);
    return def.kind === "OperationDefinition" && def.operation === "subscription";
  },
  wsLink,
  httpLink,
);

const apollo = new ApolloClient({ link, cache: new InMemoryCache() });

const sub = apollo.subscribe({
  query: gql`
    subscription OnOrderChanges($pattern: String!) {
      events(subject: $pattern) {
        id
        event
        occurredAt
        entityId
        data
      }
    }
  `,
  variables: { pattern: "orders.order.status_changed.*" },
});

sub.subscribe({ next: ({ data }) => console.log(data.events) });

7. What you just exercised

  • A durable JetStream stream named ventstream capturing all subjects under vs.t.>
  • One per-connection JetStream consumer for the subscriber, with a name like vs-t-acme-p-podA-c-01KSA...
  • When the subscriber disconnects, the consumer is deleted within milliseconds by the RAII drop guard
  • Tenant gate — events with tenant: "other" would not be delivered to a connection scoped to "acme"
