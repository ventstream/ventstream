Architecture

Two pipelines, one binary. Each independently deployable; both share the engine kernel and the runtime invariants.

Two pipelines

Pipeline A — Postgres CDC → joins → search index

Postgres ┌───────────┐ │ WAL slot │ └─────┬─────┘ │ pgoutput ▼ ┌────────────┐ │ Source │ decodes RELATION / INSERT / UPDATE / DELETE └─────┬──────┘ │ ▼ ┌────────────┐ │ Join │ forward + reverse + foreign_by_fk indexes │ engine │ sync-on-miss for absent rows └─────┬──────┘ re-emit primary doc on foreign-side change │ ▼ ┌────────────┐ │ Dispatcher │ batches events, writes DLQ on poison └─────┬──────┘ │ ▼ ┌────────────┐ │ Sink │ OpenSearch bulk, deterministic _id └────────────┘

Single-leader by design — Postgres replication slots are single-consumer. Multiple pods can run as warm standbys, but only one is active at a time. Horizontal scale on this tier is fundamentally limited; vertical scale on the WAL apply side handles tens of thousands of events/sec on commodity hardware.

Pipeline B — Durable WebSocket fan-out

SDK / app server │ publish() ▼ ┌───────────────┐ │ NATS │ acts as the event bus │ + JetStream │ durable retention └───────┬───────┘ │ ▼ ┌──────────────────┐ │ WS gateway │ one durable consumer │ (axum) │ per WS connection └────────┬─────────┘ │ ▼ WS clients

Horizontally scalable. Each pod independently subscribes to NATS, terminates its own WebSocket connections, and creates one durable JetStream consumer per active subscription. There is no shared state between pods — adding pods is purely additive.

How they fit together

The two pipelines are orthogonal. Pipeline A produces denormalized search docs from a transactional database; Pipeline B fans application events out to interested browser/mobile clients. A customer can use either, neither, or both. When both are enabled in the same process, they share the JetStream stream (the WS role bootstraps it) but otherwise don't interact.

Key design decisions

Per-connection durable consumers bespoke

The WS path creates one JetStream durable consumer per WebSocket connection, not one per service. This is unusual — standard NATS patterns use one consumer per service or queue groups for work distribution. We do it because:

  • A client that briefly disconnects (tab sleep, mobile blip, redeploy) can reconnect and replay its own cursor. The consumer state is the client's state.
  • Per-client flow control. A slow client's cursor lags, but doesn't affect anyone else.
  • Per-client ack semantics. Client confirms event N, JetStream advances that client's cursor. Crash mid-handler → reconnect → N redelivered.

The cost is N consumers per pod (N = concurrent WS clients). NATS handles tens of thousands per stream cleanly. Above that, shard streams or hybridize.

Three-layer cleanup hierarchy Cosmo-not-trap

One consumer per connection means cleanup is load-bearing. If we don't tear down consumers when clients disappear, memory leaks. The same bug bit Cosmo Router — 733 orphan consumers in production for one team. We make leaks structurally hard with three independent mechanisms:

┌──────────────────────────────────────┐ Layer 1: │ RAII drop guard in connection task │ (~ms) │ fires on EVERY exit path: │ │ graceful close, panic, ping │ │ timeout, slow-consumer eviction │ │ → js.delete_consumer(name) │ └──────────────────────────────────────┘ ▼ ┌──────────────────────────────────────┐ Layer 2: │ inactive_threshold on the consumer │ (~5 min) │ JetStream server-side auto-delete │ │ if no activity for N seconds. │ │ Catches: │ │ - kill -9 (drop guard never ran) │ │ - OOM kill │ │ - pod evicted by k8s │ └──────────────────────────────────────┘ ▼ ┌──────────────────────────────────────┐ Layer 3: │ Reaper task: every ~60s, list │ (~min) │ consumers under vs.t.>.p.{me}.c.> │ │ and diff against THIS pod's │ │ connection registry. Delete the │ │ orphans. │ └──────────────────────────────────────┘

The reaper only deletes consumers it owns (matched by p.{pod_id} in the consumer name) so each pod cleans up after itself — no cross-pod coordination needed.

Subject grammar enforced

Strict ID-last NATS subject grammar enforced by the SDK and validated by the gateway:

vs.t.{tenant}.{event}.{entity_id}

Examples:

  • vs.t.acme.orders.order.status_changed.order_123
  • vs.t.acme.users.user.profile_updated.user_456
  • vs.t.acme.billing.report.summary_generated.billing_2026_05_23 — system event

Subscribe patterns naturally fall out: vs.t.acme.orders.>, vs.t.acme.orders.order.status_changed.*. Clients see the unanchored form; the gateway prepends the tenant from auth.

Deterministic doc IDs dedupe by construction

The CDC pipeline emits one document per logical row, even when the row is re-emitted multiple times (foreign-side updates, replays). The OpenSearch sink uses a ventstream.doc.id header set by the join engine as the _id — overwriting the same document instead of leaving lifecycle copies.

The header format: {primary_table}:{primary_pk}, e.g. public.orders:["order-002"].

Opaque event payloads v1 simplicity

The data field on the event envelope is serde_json::Value — opaque to the engine. The envelope structure (id, event, tenant, entity_id, actor, occurred_at, etc.) is strict; the application-defined payload inside data is the developer's contract with their own clients. v1 doesn't validate it; a schema registry is a v1.5 feature gated on customer ask.

Crate layout

The workspace under crates/ is split by concern, not by feature. Each crate has a narrow job:

CratePurpose
ventstreamThe binary. Loads config from env, picks roles, supervises the role tasks.
ventstream-coreEngine kernel — Event, Bus, Source, Sink traits, ShutdownToken.
ventstream-protocolThe WS wire schema. Envelope, 7-segment subject grammar, validators.
ventstream-sourcesPostgres CDC source (pgoutput decoder, slot management, sync-on-miss fetcher).
ventstream-sinksOpenSearch bulk sink. Other sinks slot in here later.
ventstream-joinsThe join engine — state, reverse indexes, foreign-side re-emit, sync-on-miss.
ventstream-wsWebSocket gateway. Connection registry, per-connection JetStream consumers, three-layer cleanup.
ventstream-graphqlgraphql-transport-ws gateway. Static + dynamic schemas, federation directives.
ventstream-configYAML config loader stub. pipeline.yaml support lands here in Phase 1+.
ventstream-telemetryObservability stub. Prometheus / OpenTelemetry wiring lands here.

Workspace lints

Aggressive — designed to catch real bugs early. These apply to every crate in the workspace:

[workspace.lints.rust]
unsafe_code = "forbid"

[workspace.lints.clippy]
mem_forget        = "deny"
unwrap_used       = "deny"
expect_used       = "deny"
panic             = "deny"
todo              = "deny"
unimplemented     = "deny"
indexing_slicing  = "deny"

Tests can use unwrap / expect under a localized #[allow(...)]. Production code paths cannot.

What's intentionally not here

  • No gRPC SDK ingest path. Developers publish directly to NATS via @ventstream/sdk. The "engine ingest" gateway we sketched early on was rejected — too many debuggable layers.
  • No router code. VentStream is a subgraph / gateway, not a federation router. Apollo Router and Cosmo Router are the routers; we cooperate with them via standards (graphql-transport-ws + Apollo Federation v2 SDL).
  • No schema registry for data. v1 keeps payloads opaque. Customers can layer Zod or similar client-side.
  • No persistent state on Pipeline A. Restart = WAL replay from the last LSN. redb-backed state is a roadmap item.
