GraphQL gateway

Speak graphql-transport-ws natively so Apollo Client connects out of the box, with no custom Link and no separate socket lifecycle. Optional: declare typed subscription fields in YAML and ship a federation-conformant subgraph.

Why this exists

The native VentStream WS protocol works great if you're starting from scratch — connect, hello, subscribe, receive events. But the most common situation isn't a greenfield: customers already have Apollo Client wired up to their GraphQL server. Asking them to "also maintain a separate WebSocket connection cycle for VentStream events" is friction they won't accept.

The GraphQL gateway exposes a standard graphql-transport-ws endpoint that any Apollo Client setup recognizes natively. The developer's existing split() link configuration just adds VentStream as the subscription destination — no custom transport, no custom SDK, no separate connection management.

Two schema modes

Model 1 — Generic schema default

One subscription field, payload is the full envelope. The developer doesn't write any GraphQL schema. Apollo codegen produces typed hooks for the envelope; data is JSON the developer casts client-side.

type Subscription {
  events(subject: String!): Event!
}

type Event {
  id: ID!
  event: String!
  tenant: String!
  entityId: String!
  actor: Actor
  occurredAt: DateTime!
  receivedAt: DateTime!
  schemaVersion: Int!
  data: JSON
  metadata: Metadata!
  subject: String!
}

Client side:

subscription OnOrderChanges($pattern: String!) {
  events(subject: $pattern) {
    id
    event
    occurredAt
    entityId
    data         # JSON scalar — cast client-side
  }
}

Model 2 — Typed subscriptions via manifest opt-in

Set VS_GRAPHQL_SUBSCRIPTIONS=path/to/vs-subscriptions.yaml and the gateway builds a dynamic schema with typed subscription fields. Apollo codegen produces hooks where data is fully typed; federation routers can introspect the schema with entity references.

# vs-subscriptions.yaml
subscriptions:
  # Inline return type — VentStream owns the full payload.
  - name: orderStatusChanged
    description: "Fires when an order's status transitions."
    args:
      - { name: orderId, type: ID, required: true }
    return_type:
      kind: inline
      name: OrderStatusChange
      fields:
        - { name: orderId,   type: ID,       required: true, source: "{args.orderId}" }
        - { name: from,      type: String,   required: true, source: "$data.from" }
        - { name: to,        type: String,   required: true, source: "$data.to" }
        - { name: changedAt, type: DateTime, required: true, source: "$event.occurredAt" }
    subject: "orders.order.status_changed.{args.orderId}"

  # Federated entity reference — router stitches the rest.
  - name: orderUpdated
    description: "Federated entity ref — router stitches remaining Order fields."
    args:
      - { name: orderId, type: ID, required: true }
    return_type:
      kind: entity_ref
      type: Order
      key:
        id: "{args.orderId}"
    subject: "orders.order.*.{args.orderId}"

Source expression mini-DSL

Inside the manifest's subject templates and inline source fields, three substitution forms:

ExpressionMeaningResult type
{args.NAME}Value from subscription argsString
$data.PATHDot-path into the event's data JSONJSON (any)
$event.FIELDEnvelope field — id, event, entityId, tenant, occurredAt, receivedAt, subject, schemaVersionString or Int
literalBare string passes throughString

Examples:

  • "{args.orderId}" — set this field to whatever the client passed as orderId
  • "$data.from" — extract data.from from the published event
  • "$data.address.city" — drill into nested JSON
  • "$event.occurredAt" — set this field to the envelope's occurred_at

Apollo Client integration

This is the entire integration — same code a developer would write for any GraphQL endpoint:

import { ApolloClient, InMemoryCache, HttpLink, split, gql } from "@apollo/client";
import { GraphQLWsLink } from "@apollo/client/link/subscriptions";
import { createClient } from "graphql-ws";
import { getMainDefinition } from "@apollo/client/utilities";

const httpLink = new HttpLink({
  uri: "http://127.0.0.1:4041/graphql",
  // HTTP queries authenticate via headers (introspection, availableSubjects)
  headers: { Authorization: "Bearer demo", "X-VS-Tenant": "acme" },
});

const wsLink = new GraphQLWsLink(
  createClient({
    url: "ws://127.0.0.1:4041/graphql/ws",
    // WS subscriptions authenticate via connection_init payload
    connectionParams: () => ({ authToken: "demo", tenant: "acme" }),
  }),
);

const link = split(
  ({ query }) => {
    const def = getMainDefinition(query);
    return def.kind === "OperationDefinition" && def.operation === "subscription";
  },
  wsLink,
  httpLink,
);

export const apollo = new ApolloClient({ link, cache: new InMemoryCache() });

Subscribe with the typed field from the manifest:

apollo.subscribe({
  query: gql`
    subscription OnStatus($id: ID!) {
      orderStatusChanged(orderId: $id) {
        orderId
        from
        to
        changedAt
      }
    }
  `,
  variables: { id: "order_001" },
}).subscribe({
  next({ data }) {
    console.log(data.orderStatusChanged);
    // Fully typed: { orderId, from, to, changedAt }
  },
});

Discovery — availableSubjects

A query for clients to discover what they can subscribe to. The result is filtered by the connection's tenant. The manifest lives at the path pointed to by VS_GRAPHQL_MANIFEST.

query Discovery {
  availableSubjects {
    pattern
    description
    exampleEventType
  }
}

This is in addition to GraphQL's normal introspection — Apollo Sandbox / DevTools / graphql-codegen all see the full type system, and availableSubjects tells operators which patterns are intentionally exposed for subscription.

Federation Flavor B

The gateway is a federation-conformant subgraph out of the box. Both rover supergraph compose (Apollo) and wgc router compose (Cosmo) succeed against it. The subscription Type is included in the composed supergraph; entity references work with any router that supports Federation v2.4+.

Topology

Apollo Client │ ws://router/graphql ▼ ┌─────────────┐ │ Router │ parses operation, resolves federation │ (Apollo │ │ or Cosmo) │ └─────┬───────┘ │ subscription op ▼ ┌─────────────┐ ┌─────────────────┐ │ VentStream │ ◄─── │ Orders subgraph │ │ GraphQL │ _entities (entity-owning) │ gateway │ └─────────────────┘ └─────┬───────┘ │ emits { __typename: Order, id: "o-42" } ▼ router stitches Order's other fields client receives full typed payload

Entity reference example

The orderUpdated subscription in the manifest above returns an entity_ref. When an event arrives, VentStream emits:

{ "__typename": "Order", "id": "o-42" }

The router takes this representation, calls the orders subgraph's _entities resolver, and merges the result into the response delivered to the client — who sees a fully-stitched Order with all the fields it requested.

Verified end-to-end

packages/example/federation/federated-subscription-test.mjs runs:

  1. VentStream as a subgraph at :4041
  2. A mock orders subgraph (Apollo Server standalone) at :4042 owning Order @key(fields: "id")
  3. Cosmo Router at :4044 with the composed supergraph
  4. Apollo Client at the router subscribing to orderUpdated(orderId: "o-42") { id status total_cents customer_email }
  5. Publisher emits via @ventstream/sdk
  6. Client receives the full stitched Order: { id: "o-42", status: "confirmed", total_cents: 12995, customer_email: "..." }

Two gotchas worth knowing

_service { sdl } strips Subscription types. async-graphql's legacy Federation v1 behavior excludes subscription operations from the SDL emitted by _service. For composition to include subscriptions, dump the schema via regular GraphQL introspection (__schema) and feed the file to rover/wgc directly. See packages/example/federation/dump-ventstream-sdl.mjs.
Root types must be named Query and Subscription — not the async-graphql default QueryRoot / SubscriptionRoot. Without this, the composer treats VentStream's query as a separate type from sibling subgraphs and merging fails silently. The gateway already does this rename internally.

Auth (v1 — trusted token)

v1 accepts any non-empty token. JWT validation lands later. The auth seam is in auth::extract — a single function to swap.

  • WS subscriptions: tenant + token via connection_init payload (the Apollo Client connectionParams).
  • HTTP queries: tenant + token via headers (Authorization: Bearer ..., X-VS-Tenant: ...).
