Deploy & configure

Three deployment topologies, three roles, and the full environment-variable reference. v0.1 has no Helm chart yet — deploy as a standard Linux binary or in a custom container.

Deployment topologies

Single-graph, no router

Customer has a GraphQL server they already love. They want to add subscriptions. The whole VentStream story is "we are their WS endpoint." No federation router involved.

Apollo Client ──HTTP──► customer's GraphQL server (queries / mutations) │ └─WS──► VentStream gateway (subscriptions) │ ▼ NATS JetStream

Federated, Apollo Router

Customer is on Apollo Federation. VentStream slots in as a subscription-owning subgraph.

Apollo Client ──► Apollo Router ──► [customer's subgraphs] │ └► VentStream gateway │ ▼ NATS JetStream Note: Apollo Router OSS gates federated subscriptions behind a paid GraphOS license. Cosmo Router (next) is the free alternative.

Federated, Cosmo Router

Cosmo Router supports federated subscriptions in its OSS build — and Cosmo's existing WS layer has the bug VentStream was designed to fix. Drop-in replacement story is strongest here.

Apollo Client ──► Cosmo Router ──► [customer's subgraphs] │ └► VentStream gateway │ ▼ NATS JetStream

Roles

The same binary runs as any subset of the three roles via VS_ROLES. Each role is independent — they share the engine kernel but their data paths don't intersect.

RoleWhat it doesScales
cdcPostgres logical replication → join engine → OpenSearch sinkVertical only (slot is single-consumer); use warm standbys for HA
wsNative VentStream WebSocket gateway over NATS JetStreamHorizontal (stateless except local connections)
graphqlApollo-Client-compatible graphql-transport-ws gatewayHorizontal (same as ws)

When run together (VS_ROLES=ws,graphql)

The ws role bootstraps the JetStream stream on startup. The graphql role retries get_stream for up to 15 seconds, so there's no startup-order coupling between the two within the same process.

NATS / JetStream prerequisites

The WS and GraphQL roles both require NATS with JetStream enabled. Minimum dev setup:

brew install nats-server
mkdir -p /var/ventstream-jetstream
nats-server -js -sd /var/ventstream-jetstream

For production: a 3-node NATS cluster with JetStream replicas set to 3. Persistent volumes for each node's sd directory. See NATS clustering docs.

Health endpoints

Both gateway roles expose a /healthz endpoint returning {"status":"ok"}. Wire it into k8s liveness/readiness probes:

livenessProbe:
  httpGet:
    path: /healthz
    port: 4040       # or 4041 for graphql role
  initialDelaySeconds: 5
  periodSeconds: 10
readinessProbe:
  httpGet:
    path: /healthz
    port: 4040
  initialDelaySeconds: 2
  periodSeconds: 5

What's not yet built

No Docker image / Helm chart. Deploy by copying the binary into a base image and writing your own k8s manifests. This is the first roadmap item we'd add to make VentStream operationally shippable.
JWT auth is a stub. Both connection_init payloads and HTTP headers currently accept any non-empty token string. The auth seam is in auth::extract for the GraphQL role and the WS Hello handler for the native protocol. Single function to swap.
No leader election yet. The CDC role is single-consumer by Postgres design, but failover between hot-standby pods needs a Kubernetes Lease or Postgres advisory lock — neither is wired up.
Observability is a stub. The ventstream-telemetry crate exists but doesn't yet emit Prometheus metrics or OpenTelemetry traces. Connection count, consumer count, JetStream lag — none wired.
