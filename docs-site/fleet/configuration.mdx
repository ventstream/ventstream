---
title: "Managed configuration"
description: "Validate, select, and apply immutable VentStream engine configuration revisions."
---

Fleet stores non-secret engine configuration as immutable, content-addressed
revisions. A revision must validate before it can be selected, and selection is
separate from application.

```bash
ventstreamctl pipelines configurations create orders-cdc \
  --engine-config ./ventstream.yaml \
  --file joins.yaml=./joins.yaml \
  --file graphql/schema.graphql=./schema.graphql

ventstreamctl pipelines configurations list orders-cdc
ventstreamctl pipelines configurations validate orders-cdc <revision>
ventstreamctl pipelines configurations select orders-cdc <revision>
ventstreamctl pipelines configurations apply orders-cdc <revision> --wait
ventstreamctl pipelines resume orders-cdc --wait
```

The agent stages files atomically in a private configuration directory and starts
the engine with `VS_ENGINE_CONFIG` pointing at the generated `ventstream.yaml`.
For a new pipeline, the first selection creates its initial desired state as
`paused`. Applying the revision stages and validates it without starting the
engine; an explicit `resume` performs the first start. Later selections preserve
the pipeline's current run state. Rollback selects and applies a previously valid
immutable revision.

## Secret boundary

Configuration documents contain references such as `env:VS_OS_ENDPOINT`, not
credential values. Inject database passwords, API keys, TLS private keys, and other
secrets through Kubernetes Secrets or the customer's secret manager. Fleet should
be able to validate and distribute configuration without becoming a credential
vault or data-plane dependency.

Validation occurs at multiple boundaries: control-plane schema and policy checks,
agent bundle integrity checks, and engine-native semantic parsing before startup.
